# BeerDirect 数据库选型与 SQLite 可行性分析（轻量修订版）

## 说明

这份文档用于在新的轻量技术路线下，重新评估数据库方案。

新的前提条件是：
- 前端：Vue 3
- 后端：Express
- 不使用 Prisma
- 尽量减少抽象层

在这个前提下，我们要重新回答：

**SQLite 还可不可行？如果可行，应该怎么用才最合适？**

---

## 一、先说结论

## 结论 1
**SQLite 仍然可行，而且在这套轻量架构里比之前更自然。**

## 结论 2
在不使用 Prisma 的情况下，BeerDirect 第一阶段最推荐的数据库组合是：

- SQLite
- `better-sqlite3`
- 手写 SQL + 轻量查询封装

## 结论 3
SQLite 的适用前提仍然是：
- 小团队或个人内部使用
- 中低频写入
- 以来源管理、文档管理、摘要管理为主
- 没有大量并发任务同时写库

## 结论 4
如果后续出现：
- 自动采集任务明显增多
- 多人高频协作
- 线上部署更复杂
- 需要更强并发和稳定性

则再迁移到 PostgreSQL。

也就是说：

**BeerDirect 第一阶段推荐继续使用 SQLite，但用法要更朴素、更克制。**

---

## 二、为什么 SQLite 在轻量架构里更合理

在上一版方案里，SQLite 是和 Prisma 绑定讨论的。

但现在你明确不要 Prisma，实际上 SQLite 反而更贴合“少抽象”的思路。

因为现在系统会变成：
- Vue 3 前端
- Express API
- SQLite 文件数据库
- 更少的中间层

这时 SQLite 的优势会更明显：

### 1. 没有额外数据库服务
本地开发非常直接。

### 2. 不需要 ORM 才能工作
可以直接建表、写 SQL、查数据。

### 3. 很适合 BeerDirect 当前的数据类型
当前数据主要是：
- 来源
- 观察名单
- 文档元信息
- Markdown 摘要
- 条目
- 标签关系

这些都不是超重事务场景。

### 4. 部署模型简单
如果第一阶段主要是本地开发、单机服务、内部工具，SQLite 非常顺手。

---

## 三、为什么不建议现在为了“规范”而直接上 PostgreSQL

PostgreSQL 当然更强，但 BeerDirect 当前阶段更需要的是：
- 尽快跑起来
- 架构足够清楚
- 不要引入过多基础设施负担

如果你现在直接上 PostgreSQL，会额外带来：
- 数据库安装与管理
- 环境配置
- 连接管理
- 迁移维护
- 本地与线上一致性处理

这些当然都能做，但对 BeerDirect 当前阶段来说，性价比未必最高。

所以更合理的路线是：

### 现在
先 SQLite

### 将来
到确实需要时再迁 PostgreSQL

这比一上来为了“长期正确”而增加复杂度更现实。

---

## 四、SQLite 最适合承载哪些表

BeerDirect 第一阶段里，下面这些内容非常适合存 SQLite：

## 1. sources
来源定义表

## 2. watchlists
平台观察名单表

## 3. documents
文档元信息表

## 4. digests
Markdown 摘要表

## 5. entries
新闻 / 技术 / 平台观察条目表

## 6. tags 与关系表
标签和多对多关系表

这些表的共同特点是：
- 结构清晰
- 数据量前期可控
- 查询主要是后台管理与筛选
- 写入并发有限

SQLite 很适合干这个活。

---

## 五、SQLite 不适合承担什么

在 BeerDirect 里，SQLite 第一阶段不太适合承担这些重负载内容：

## 1. 高频抓取任务并发写入
如果未来多个采集器同时高频写库，SQLite 会越来越吃力。

## 2. 重型任务队列
不建议把复杂任务队列系统直接压在 SQLite 上。

## 3. 海量运行日志
运行日志更适合文件、按日切分，或后续独立日志系统。

## 4. 特别复杂的全文搜索
第一阶段可以先不用复杂全文搜索，或者只做基础搜索。

---

## 六、不用 Prisma 之后，数据库访问怎么做

既然不用 Prisma，就要回答一个实际问题：

**数据库操作层怎么写，才不会变得很乱？**

## 推荐方式

### 方案
- 用 `better-sqlite3`
- 用 `schema.sql` 管理初始表结构
- 用 `migrations/` 保存增量 SQL
- 用 `queries/` 或 `repositories/` 组织查询逻辑

## 示例结构

```text
server/
├── src/
│   ├── db/
│   │   ├── index.ts
│   │   ├── schema.sql
│   │   ├── migrations/
│   │   └── queries/
│   │       ├── sources.ts
│   │       ├── watchlists.ts
│   │       ├── documents.ts
│   │       ├── digests.ts
│   │       └── entries.ts
```

## 这样做的好处
- 不重
- SQL 直观
- 不会到处散写数据库逻辑
- 以后迁 PostgreSQL 时也有清晰边界

---

## 七、是否要手写全部 SQL

## 建议：要写 SQL，但不要无组织地写

也就是说：
- 可以不用 ORM
- 但不要在 Express 路由里直接到处拼 SQL

推荐模式：
- route 负责接参和返回
- service 负责业务逻辑
- db/queries 负责数据库操作

例如：

```text
routes -> controllers -> services -> db/queries
```

这已经足够清晰，也不会太重。

---

## 八、SQLite 的实际使用建议

如果 BeerDirect 第一阶段采用 SQLite，我建议遵守下面这些规则：

## 1. 原始 PDF 不进数据库
数据库只存：
- 文件路径
- 来源
- 类型
- 状态
- 摘要关联

## 2. Markdown 摘要可以进数据库
因为这正是系统后续检索和管理的核心。

## 3. 大字段和元数据分开考虑
如果某些摘要以后变得很长，可以评估是否拆表或存文件。

## 4. 写入任务要串行或低并发
至少第一阶段尽量避免多个任务一起猛写。

## 5. 设计时预留 PostgreSQL 迁移空间
不要依赖太多 SQLite 私有写法。

---

## 九、迁移 PostgreSQL 的判断信号

下面这些信号一出现，就说明 SQLite 差不多到边界了：

## 信号 1
自动抓取任务显著增多，开始频繁写入。

## 信号 2
不止一个人重度使用后台。

## 信号 3
开始要做稳定线上部署，而不是单机内部服务。

## 信号 4
开始要复杂搜索、复杂统计、复杂权限。

## 信号 5
开始引入 worker、队列、批处理流水线。

## 十、BeerDirect 当前阶段的明确建议

如果按你现在要求的极简路线，我的建议非常明确：

### 第一阶段推荐组合
- 数据库：SQLite
- 访问库：better-sqlite3
- 表结构管理：SQL 文件
- 迁移方式：手写 migration SQL
- 查询方式：模块化 SQL 查询层

### 为什么这是当前最优解
- 足够轻
- 可控
- 没有 ORM 额外心智负担
- 和 Vue 3 + Express 非常匹配
- 非常适合内部研究管理系统

---

## 十一、需要注意的代价

不用 Prisma、直接 SQLite，并不意味着没有代价。

你需要接受这几点：

### 1. 你要自己更认真管理表结构
没有 ORM 帮你兜底。

### 2. 数据库变更需要自己写 migration SQL
这会更直接，但也更需要纪律。

### 3. 类型安全会少一些
尤其是 compared with ORM 生成类型的体验。

但如果你的目标是“尽量简化架构”，这些代价是合理的。

---

## 十二、明确结论

对 BeerDirect 当前阶段，在你指定的新约束下，我的明确建议是：

### 数据库方案
- **SQLite**
- **better-sqlite3**
- **手写 SQL + 轻量查询封装**

### 是否可行
- **可行**
- 而且是当前最符合“尽量简化架构”目标的方案

### 什么时候升级
- 当 BeerDirect 从“内部研究系统”成长为“更稳定、更并发、更自动化的平台”时，再迁 PostgreSQL

所以当前可以非常明确地说：

**SQLite 在 Vue 3 + Express + 无 Prisma 的 BeerDirect 第一阶段架构里，是可行且推荐的。**
