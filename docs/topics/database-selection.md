# BeerDirect 数据库选型与 SQLite 可行性分析（第一版）

## 目标

这份文档用于回答 BeerDirect 当前技术实现中的一个核心问题：

**SQLite 是否适合作为第一阶段数据库？**

同时，也需要明确：

- BeerDirect 当前真正需要什么数据库能力
- SQLite 的适用边界在哪里
- 什么时候应该迁移到 PostgreSQL

---

## 一、先说结论

## 结论 1
**SQLite 作为 BeerDirect 第一阶段主数据库，是可行的。**

## 结论 2
对于 BeerDirect 目前的产品形态，SQLite 甚至是一个很合适的起点，因为它：
- 简单
- 成本低
- 开发快
- 本地部署方便
- 和 Prisma / Next.js 组合顺畅

## 结论 3
但 SQLite 的前提是：
- 当前是内部研究系统 / 管理台
- 并发写入不高
- 使用人数少
- 没有复杂的高频任务队列
- 不需要重度全文搜索或大规模分析型查询

## 结论 4
如果 BeerDirect 后续演化成：
- 多人频繁协作
- 自动抓取任务大量并发写入
- 文档数量快速增长
- 需要更稳定的服务端部署
- 需要权限、多环境、队列、搜索等更完整基础设施

那么应迁移到 **PostgreSQL**。

---

## 二、BeerDirect 第一阶段对数据库的真实需求

先不要从“数据库哪个好”出发，而要从“BeerDirect 现在要存什么”出发。

## 第一阶段核心存储对象

### 1. 来源定义
例如：
- 来源名称
- 来源分类
- 平台类型
- 优先级
- 链接
- 备注

### 2. 观察名单
例如：
- 小红书账号
- 公众号
- Untappd 品牌池
- 技术作者
- 原料商

### 3. 文档记录
例如：
- PDF 文件元信息
- 原始来源
- 类型
- 处理状态
- 路径或链接

### 4. Markdown 摘要 / Digest
例如：
- 提炼后的核心内容
- 页码引用
- 文档关联
- 主题标签

### 5. 内容条目
例如：
- 新闻条目
- 技术文章条目
- 平台观察记录
- 品牌更新记录

### 6. 标签与关系
例如：
- hops
- yeast
- haze
- packaging
- market
- china

这些数据的共同特点是：
- 结构化程度中等
- 写入频率不算特别高
- 查询以后台管理和研究筛选为主
- 事务需求有，但不极端复杂

这正是 SQLite 可以胜任的典型场景。

---

## 三、为什么 SQLite 适合 BeerDirect 第一阶段

## 1. 零运维成本
SQLite 不需要单独启动数据库服务。

这意味着：
- 本地开发非常方便
- 不需要额外安装和维护 Postgres
- 初期心智负担小

对 BeerDirect 这种刚起步的项目，这是很大的优势。

## 2. 开发速度快
如果你现在更重要的是：
- 快速把表结构搭起来
- 快速验证来源管理和文档管理流程
- 快速做后台界面

SQLite 会比“先把数据库基础设施搭很复杂”更高效。

## 3. 与 Prisma 配合顺手
如果前面采用：
- Next.js
- Prisma
- SQLite

会形成一个很轻的开发体验：
- schema 清晰
- migration 简单
- CRUD 开发快

## 4. 本地研究系统非常适合
BeerDirect 当前本质上更像：
- 内部资料系统
- 研究型后台
- 知识整理工作台

而不是：
- 高并发在线交易系统
- 实时协同产品
- 大型 SaaS 平台

所以 SQLite 在这个阶段非常匹配。

## 5. 后续迁移成本可控
如果一开始用 Prisma 做数据模型，后面从 SQLite 迁移到 PostgreSQL 的路径相对清晰。

也就是说：
- SQLite 不一定是终局
- 但它可以是一个非常合理的起点

---

## 四、SQLite 的核心问题在哪里

SQLite 可行，不代表没有边界。

## 1. 并发写入能力有限
SQLite 最大的现实限制之一，就是写入并发能力不强。

它更适合：
- 少量用户
- 中低频写入
- 后台录入和处理

不太适合：
- 大量定时抓取同时写库
- 多个 worker 高频并发写入
- 多人同时大量编辑

对于 BeerDirect 来说，这意味着：

### 现在可以
- 手工录入
- 中等频率脚本写入
- 小规模自动导入

### 以后可能不够
- 10+ 个抓取任务同时跑
- 多个自动摘要任务同时写库
- 多人协同编辑和审核

## 2. 部署和文件锁问题
SQLite 是文件数据库。

这意味着：
- 本地开发非常舒服
- 单机部署也可以
- 但如果部署环境复杂，文件锁和持久化管理会更敏感

特别是：
- 无状态云函数环境
- 多实例部署
- 容器重建频繁

都不如 PostgreSQL 稳。

## 3. 查询和分析能力上限较低
如果 BeerDirect 后续需要：
- 更复杂的全文搜索
- 更大的关联查询
- 更重的分析型视图
- 更复杂的权限和审计

SQLite 不是最理想选择。

## 4. 生态与团队协作上限
一旦项目从“个人 / 小团队工具”变成“稳定服务”，PostgreSQL 的团队协作体验会明显更好。

---

## 五、SQLite 在 BeerDirect 里适合承担什么

## 第一阶段非常适合的内容
- 来源表
- 标签表
- 观察名单表
- 文档表
- 摘要表
- 条目表
- 小规模任务状态表

## 第一阶段不建议压得太重的内容
- 大规模全文搜索索引
- 高频任务队列表
- 大量日志明细
- 高并发抓取写入流水

换句话说：

**SQLite 很适合做 BeerDirect 的“知识主库”，但不适合未来承担所有高频任务型负载。**

---

## 六、对 BeerDirect 的实际建议

## 推荐方案

### 第一阶段
- 主数据库：SQLite
- ORM：Prisma
- 文件存储：本地文件系统或明确的数据目录
- 搜索：先做基础筛选，不急着上复杂全文搜索

### 第二阶段
当出现以下任一情况时，开始准备迁移 PostgreSQL：
- 多人同时使用
- 定时采集任务显著增多
- 文档与条目数量增长很快
- 需要更稳定的部署环境
- 需要审计、权限、任务调度和更复杂查询

### 第三阶段
- 主数据库切 PostgreSQL
- SQLite 仅用于本地开发或临时环境

---

## 七、是否要一开始直接上 PostgreSQL

## 可以，但未必值得

如果你现在一开始就上 PostgreSQL，当然也不是错。

它的优点是：
- 更稳
- 更适合长期演进
- 更适合服务端部署
- 并发和扩展性更好

但问题在于：
- 初期复杂度上升
- 开发门槛略高
- 对当前阶段的真实收益未必足够大

所以对 BeerDirect，我更倾向于：

### 如果当前目标是尽快做出来
先 SQLite

### 如果当前目标是马上做成稳定在线协作系统
直接 PostgreSQL

而按目前仓库状态和需求描述看，更像前者。

---

## 八、推荐的迁移判断信号

当出现下面这些信号时，就说明该从 SQLite 迁移到 PostgreSQL 了。

## 信号 1：写入任务明显增多
例如：
- 定时抓取越来越多
- PDF 处理流水线增多
- 自动摘要和打标签任务增多

## 信号 2：不止一个人在重度使用
例如：
- 多人编辑来源
- 多人维护摘要
- 多人同时做审核

## 信号 3：部署方式开始复杂化
例如：
- 想部署到稳定线上环境
- 想多环境管理
- 想做 staging / production 区分

## 信号 4：开始需要更强搜索 / 统计能力
例如：
- 复杂全文搜索
- 大量标签交叉查询
- 数据统计报表

## 信号 5：开始引入后台任务系统
例如：
- queue
- worker
- 大量抓取器
- 批处理流水线

## 九、推荐的数据组织方式

即使用 SQLite，也建议从一开始就把数据库边界设计清楚。

## 建议原则

### 1. 文本大内容与元数据分离
例如：
- 摘要正文可以存数据库
- 原始 PDF 文件本体不要直接塞进数据库
- 原始文件放磁盘或对象存储
- 数据库只存路径、元信息、状态

### 2. 任务状态表不要设计得太重
第一阶段任务状态可简单，但别把大量运行日志全压数据库。

### 3. 标签和关系表要规范
因为 BeerDirect 后续很依赖：
- 标签
- 主题
- 来源关系
- 文档关系

这部分结构一开始就该设计清楚。

## 十一、SQLite 的实践建议

如果决定第一阶段用 SQLite，建议同时遵守这些原则：

## 1. 不把它当永久终局
设计时默认未来可能迁移 PostgreSQL。

## 2. 所有数据库访问都走 ORM
尽量不要满地写原生 SQL。

## 3. 避免过度依赖 SQLite 特性
这样以后迁移更平滑。

## 4. 大文件不要进库
PDF、图片、原始附件走文件路径。

## 5. 重任务与主库逻辑分离
抓取、清洗、转换任务尽量做成独立脚本，不要一开始把数据库耦合得太重。

---

## 十二、明确结论

对 BeerDirect 当前阶段，我的明确建议是：

### 数据库建议
- **第一阶段：SQLite**
- **第二阶段：PostgreSQL（条件触发式迁移）**

### 为什么 SQLite 可行
- 当前数据模型并不复杂
- 当前更像内部研究系统
- 写入并发需求还不高
- 开发速度和维护成本更重要

### SQLite 的边界
- 不适合未来重并发写入
- 不适合复杂部署和多实例场景
- 不适合承担越来越重的任务系统

所以：

**SQLite 对 BeerDirect 第一阶段是可行且推荐的，但要从第一天就按“未来可迁移”来设计。**
